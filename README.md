# Next.js + Postgres + pgAdmin (Dockerized)

A Cyberpunk 2077-styled contacts manager: a Next.js (App Router) app backed
by Postgres via Prisma, orchestrated with Docker Compose. Three containers:

| Service   | Image                  | Purpose                          | Default URL             |
|-----------|-------------------------|-----------------------------------|--------------------------|
| `web`     | built from `Dockerfile` | Next.js app                       | http://localhost:3000    |
| `db`      | `postgres:16-alpine`    | Postgres database                 | localhost:5432 (psql)    |
| `pgadmin` | `dpage/pgadmin4`        | Web UI for administering Postgres | http://localhost:5050    |

## Prerequisites

- Docker Desktop (or Docker Engine + Compose plugin)

## Setup

1. Copy the environment template and adjust values as needed:

   ```bash
   cp .env.example .env
   ```

2. Build and start all three containers:

   ```bash
   docker compose up --build
   ```

3. On first run only, no tables exist yet — create and apply the initial
   Prisma migration:

   ```bash
   docker compose exec web npx prisma migrate dev --name init
   ```

   This generates `prisma/migrations/<timestamp>_init/` (commit it to git).
   On every subsequent `docker compose up`, the `web` service automatically
   runs `prisma migrate deploy` before starting, so any committed migrations
   are applied without a manual step.

4. Once running:
   - Contacts app: [http://localhost:3000](http://localhost:3000)
   - Health check (verifies the app can reach Postgres via Prisma): [http://localhost:3000/api/health](http://localhost:3000/api/health)
   - pgAdmin: [http://localhost:5050](http://localhost:5050)
     - Log in with `PGADMIN_DEFAULT_EMAIL` / `PGADMIN_DEFAULT_PASSWORD` from `.env`.
     - A server named **Docker Postgres** is pre-registered (see `pgadmin/servers.json`). On first connection you'll be prompted for the Postgres password — use `POSTGRES_PASSWORD` from `.env`.

5. Stop everything:

   ```bash
   docker compose down
   ```

   Add `-v` to also delete the Postgres/pgAdmin data volumes:

   ```bash
   docker compose down -v
   ```

## How it fits together

- All three services share a single Docker network (`app-network`) defined
  in [docker-compose.yml](docker-compose.yml), so containers reach each
  other by service name (`db`, `web`, `pgadmin`) rather than `localhost`.
- The `web` container talks to Postgres using `DATABASE_URL`, which points
  at the `db` service's hostname on the internal network:
  ```
  postgresql://<user>:<password>@db:5432/<database>
  ```
- `web` waits for `db` to report healthy (via a `pg_isready` healthcheck)
  before starting.
- Postgres data persists in the named volume `postgres_data`; pgAdmin's own
  settings persist in `pgadmin_data`. Both survive `docker compose down`
  (removed only with `down -v`).

## Application

A single Postgres-backed resource — **contacts** — with full CRUD:

| Route                     | Purpose                                      |
|----------------------------|-----------------------------------------------|
| `GET /`                    | List all contacts in a HUD-styled table       |
| `GET /contacts/new`        | Form to create a contact                      |
| `GET /contacts/[id]/edit`  | Form to edit/delete an existing contact       |
| `GET /api/health`          | DB connectivity check (via Prisma)            |

Creating/editing goes through Next.js Server Actions
([app/contacts/actions.ts](app/contacts/actions.ts)), validated server-side
with [Zod](lib/validations/contact.ts) — first name, last name, and email
are all mandatory, email must be a valid address and unique. Deleting is
gated by a confirmation dialog ([components/DeleteButton.tsx](components/DeleteButton.tsx)).

## Dockerfile stages

The [Dockerfile](Dockerfile) is multi-stage:

- **`base`** – installs `openssl`/`libc6-compat` (required by Prisma's query
  engine on Alpine), copies `prisma/schema.prisma` in *before* `npm install`
  (so its `postinstall: prisma generate` hook has a schema to read), then
  installs npm dependencies. Shared by other stages.
- **`dev`** – used by `docker-compose.yml` for local development. The
  project directory is bind-mounted into the container so `next dev`
  hot-reloads on file changes. `docker-compose.yml` runs
  `prisma migrate deploy` before `npm run dev` on every start, applying any
  committed migrations.
- **`builder`** – runs `next build` (production build, `output: "standalone"`).
- **`runner`** – final production image: copies the standalone build
  output, runs as a non-root user. Also explicitly copies
  `node_modules/.prisma`, `node_modules/@prisma/client`, and `prisma/` from
  the builder stage — Next's standalone output tracing doesn't reliably
  pick up Prisma's native query-engine binary, so this is copied by hand
  (and `openssl`/`libc6-compat` are installed here too, since this is the
  stage that actually loads the engine at runtime).

To build and run the production image directly (outside Compose, or when
deploying):

```bash
docker build -t nextjswebsite:prod .
docker run -p 3000:3000 --env DATABASE_URL=postgresql://... nextjswebsite:prod
```

(`docker build` with no `--target` builds through to the last stage,
`runner`.) For a production Compose setup, add an override file that sets
`build.target: runner` on the `web` service and drops the bind-mount
volumes.

## Prisma workflow

- **Schema**: [prisma/schema.prisma](prisma/schema.prisma) defines the
  `Contact` model, mapped to a `contacts` table.
- **Create a new migration** after changing the schema:
  ```bash
  docker compose exec web npx prisma migrate dev --name <description>
  ```
- **Apply committed migrations** without generating a new one (what
  `docker-compose.yml` runs automatically on `web` startup):
  ```bash
  docker compose exec web npx prisma migrate deploy
  ```
- **Browse/edit data with Prisma Studio**:
  ```bash
  docker compose exec web npx prisma studio
  ```
  (add a port mapping for `5555` if you want to reach it from the host, or
  run it locally against `localhost:5432` instead.)
- **Regenerate the Prisma Client** (normally automatic via the
  `postinstall` script):
  ```bash
  docker compose exec web npx prisma generate
  ```

## Environment variables

Defined in `.env` (see `.env.example` for defaults):

| Variable                  | Used by         | Description                                  |
|----------------------------|-----------------|-----------------------------------------------|
| `POSTGRES_USER`            | `db`, `web`     | Postgres superuser/app user                   |
| `POSTGRES_PASSWORD`        | `db`, `web`     | Postgres password                             |
| `POSTGRES_DB`              | `db`, `web`     | Database name created on first boot           |
| `POSTGRES_PORT`            | `db`            | Host port mapped to Postgres's `5432`         |
| `DATABASE_URL`             | `web`           | Full connection string used by the app        |
| `WEB_PORT`                 | `web`           | Host port mapped to the Next.js app's `3000`  |
| `PGADMIN_DEFAULT_EMAIL`    | `pgadmin`       | Login email for the pgAdmin UI                |
| `PGADMIN_DEFAULT_PASSWORD` | `pgadmin`       | Login password for the pgAdmin UI             |
| `PGADMIN_PORT`             | `pgadmin`       | Host port mapped to pgAdmin's internal `80`   |

`.env` is git-ignored — never commit real credentials. Change all default
passwords before using this outside of local development.

## Local development without Docker (optional)

```bash
npm install
npm run dev
```

Requires a reachable Postgres instance and a `DATABASE_URL` in your shell
environment or a `.env.local` file.
